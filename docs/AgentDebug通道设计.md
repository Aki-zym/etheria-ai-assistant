# Agent Debug 通道设计

> v1 · 2026-09-06
> 定位：作为《Etheria升级总计划》的**并行工作包 DX**。旧仓库（EtheriaAssistant）立即受益——当前新功能仍在这里开发调试；DX-4 起同一协议接入 EtheriaMaa 主线。

---

## 一、问题定义与第一性原则

理想的调试循环：**改一行 → 跑一段 → 同刻看（日志 + 截图）→ 下结论 → 再改。**

第一性原则：调试的本质是把 Agent 的"感知-行动"循环与被测系统对齐到**同一条时间轴**。对照现状，缺口归结为四个根因：

| 根因 | 表现 |
|---|---|
| 1. 阻塞执行 | Agent 一旦前台等进程结束，就交出了观察权；挂住的任务烧满超时预算 |
| 2. 观测不同步 | 日志与截图各记各的时刻，"打印这行日志时画面是什么"无法回答 |
| 3. 卡住不产出观测 | 死等 = 零信息；脚本里无上限的等待让"卡住"永远静默 |
| 4. 流程靠临场发挥 | 每个会话重新发明调试方法，质量取决于 Agent 当场想到什么 |

设计总纲：**永不阻塞、时刻对齐、挂死必出片、一切有标准。**

## 二、现状能力盘点（不新建任何东西，今天能做到哪一步）

| 理想动作 | 现状 | 缺口 |
|---|---|---|
| 输入一段代码 → 等回复 | ✓ 每次工具调用即一问一答，粒度足够 | — |
| 看输出文本 | ✓ 前台跑完看全量；或后台运行 + 任意时刻读输出文件，且结束时自动回报 | △ 靠 Agent 自觉选后台 |
| 对照游戏截图 | ✓ 随时可截、随时可看（旧仓库截图栈 / EtheriaMaa 的截屏脚本均已验证） | △ 截图与日志不同刻，对齐靠手工 |
| 长代码边跑边盯 | ✓ 机制可行（后台运行 + 轮流读输出文件） | △ 无节奏标准；挂住时只会干等 |
| 卡住半天 | ✗ 前台烧满超时；脚本无上限等待；无"静默→自动转观测"的兜底 | 根因 1/3/4 叠加 |

**结论**：理想调试状态在当前环境下机制上已具备约八成，且"傻等"主要是行为问题（根因 1/4），协议先行即可立竿见影。真正要建的是两成：**时刻对齐、挂死转现场、标准化步进**。

## 三、通道设计（四层）

### L0 · 调试协议（行为层，零代码，先落地）

写入 `.claude/skills/agent-debug/`（技能形式，两个仓库共用同一份），规则五条：

1. 预计超过 10 秒的运行**一律后台执行**；前台只允许跑秒回的探针（截一帧、读状态、跑一个断言）。
2. 轮询节奏：每 5~10 秒读一次 console.log；**日志静默超过 15 秒 → 先截帧再判断，禁止空等**。
3. 证据规则：任何"成功 / 失败"结论必须有**日志行 + 同刻截图**两种证据，缺一不下结论。
4. 超预算即止损：到达预算、或连续两次干预无效 → 停止 + 收现场包，带证据回来讨论，不做第三次盲跑。
5. 会话产物不入库（`debug/runs/` 进 .gitignore）。

### L1 · 统一运行器（工具层，核心交付）

入口 `python scripts/agent_debug.py …`（EtheriaMaa 侧同语义包装 app/main.py）：

| 命令 | 作用 |
|---|---|
| `run <任务ID或脚本路径> [参数] [--budget 秒] [--shot-every 秒]` | 后台启动被测程序，自任监护进程 |
| `shot [标签]` | 立即截一帧，存入当前会话 |
| `stop` | 优雅停止当前会话进程 |
| `list` | 列出可跑入口（旧仓库读 core/tasks.py 注册表） |

会话目录（一切文件皆证据）：

```
debug/runs/20260906-153000-主线/
├── console.log     # UTF-8 行缓冲，每行带 [时:分:秒.毫秒]
├── state.json      # 监护进程持续刷新：任务/进程存活/最近日志时刻/最新帧路径/死因
└── frames/         # 0001_153002_原因.png（序号_时刻_原因）
```

**看门狗——把"挂死"变成"现场包"**：全局预算到期，或 console.log 静默超阈值（默认 20 秒，按任务可放宽）→ 自动截最后一帧 + 抄日志尾 + 死因写入 state.json → 停止进程（先发优雅停止信号，3 秒不退则终止进程树）。Agent 读一个 state.json 就知道该看什么、发生了什么。

工程细节：子进程强制 UTF-8（解释器 utf8 模式 + 环境变量双保险）、输出直写文件不经控制台编码、全部日志强制即时刷出；用当前解释器启动子进程，自动带上正确的虚拟环境。

### L2 · 时刻对齐（观测层）

1. **日志时刻归一**：统一日志格式（毫秒级时间戳 + 直写文件），旧仓库日志已带时刻，只做格式收敛。
2. **关键时刻自动存帧**：五个时机自动截帧——动作前、动作后、等待开始、等待超时、识别命中。这与总计划第三章"贯穿不变量"（失败落盘、结构化回调）是**同一套钩子的旧仓库轻量版**，不是平行系统。
3. **对齐规则**：帧文件名含时刻，对照时取"与日志行时刻最近的帧"；state.json 永远指向最新帧。
4. 迁到 MaaFW 后由引擎的结构化回调与失败存图直接承接，通道只换数据源、协议不变。

### L3 · 步进会话（交互层，"一行一观察"）

解决"跑在半路想看一眼"：

- `run --step` 模式：在每个步进检查点（动作前后、每轮扫描开头）暂停，等待指令。
- **控制通道 = 文件**，不用端口、不用交互终端（Windows 下最稳）：
  - Agent 写 `debug/session/control.json`：`{"cmd": "step | continue | shot | stop"}`
  - 运行器写 `debug/session/status.json`：当前暂停点、正在等什么、最近帧路径。
- 不开 `--step` 时行为与 L1 全速运行相同；检查点空转成本 ≈ 读一次文件的修改时间。
- 落点：检查点钩子挂在 Bot 基类与任务注册表的运行器包装层，新脚本默认继承，业务代码零改动。

### 明确不做（范围纪律）

- 不做常驻服务 / 端口 / 自绘终端——文件通道在 Windows 上最稳且可随时人工查看。
- 不替代单元测试与静态校验（EtheriaMaa 的双层测试模式优先于手调）。
- 不为调试在业务代码里开特例——检查点与存帧都是通用钩子。
