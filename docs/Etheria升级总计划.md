## 一、总体决策

| 决策 | 内容 | 状态 |
|---|---|---|
| 引擎 | 采用 MaaFramework 作为核心引擎，不自研识别/调度引擎 | 沿用既有决策，P0 已验证 |
| 控制器 | 主线只开发 PC 客户端：系统级后台画面流截图 + 窗口消息输入 | **本次变更** |
| 模拟器 | 整体封存，等待模拟器厂商支持伊瑟最新版本后按重启清单接入 | **本次变更** |
| 分工 | 简单流程写成管线数据；复杂逻辑进自定义扩展；前端只做面板与日志 | 沿用 |
| 仓库 | 开发主战场 = `EtheriaMaa` 仓库；`EtheriaAssistant` 冻结为旧版运行时 | **本次明确** |

**封存为什么零成本（架构保证）**：管线资源、任务声明、自定义逻辑三者都与控制器解耦——控制器只是"换一双眼睛和一双手"。封存期间 PC 主线写下的每一条管线，未来模拟器可用时原样复用；唯一的接入动作是把连接方式声明切回 ADB。

## 二、目标架构

```
┌──────────────────────────────────────────────────────┐
│ 前端：Vue3 面板                                       │
│   读 interface.json 渲染任务面板；订阅回调显示日志      │
│   （禁止编排业务流程、禁止轮询队列）                    │
├──────────────────────────────────────────────────────┤
│ 编排层：Python（MaaFramework 官方绑定）                │
│   发现游戏窗口 → 绑定资源与控制器 → 派发任务            │
│   → 消费结构化回调 → 任务进度持久化                    │
├──────────────────────────────────────────────────────┤
│ 自定义逻辑层（AgentServer，唯一逃生舱）                │
│   源网选牌决策 / 虚烬 3D 走位 / RTA 先后手判定 …        │
├──────────────────────────────────────────────────────┤
│ 游戏内容层（纯数据，零代码）                           │
│   interface.json + pipeline/*.json + image/*.png      │
├──────────────────────────────────────────────────────┤
│ 核心引擎 MaaFramework（官方维护，我方零维护）           │
│   识别 / 节奏 / 重试 / 超时 / 命中缓存 / 失败存图 内建  │
├──────────────────────────────────────────────────────┤
│ 控制器层                                              │
│   ● 现役：Win32 控制器（PC 客户端）                    │
│   ○ 封存：Adb 控制器（模拟器，见第六章）               │
└──────────────────────────────────────────────────────┘
```

**依赖红线**：只允许上层依赖下层；同一套内容层资源供两种控制器共用；前端永不反向调度业务。

**目录职责**（以 EtheriaMaa 骨架为基座扩容）：

```
EtheriaMaa/                 ← 开发主战场
├── assets/interface.json   ← 唯一任务入口清单（GUI 与 CLI 共用）
├── assets/resource/        ← 管线 + 模板图 + OCR 模型
├── agent/                  ← 自定义识别 / 自定义动作
├── app/                    ← 编排 + 前端桥（P3 时前端代码迁入）
└── tests/                  ← 静态 + 集成双层测试

EtheriaAssistant/           ← 旧版运行时：迁移期并行可用；
                               只修致命问题不加功能；素材单向搬出
```

## 三、每一轮的执行流程（一张图的生命周期）

先讲清引擎每一轮做什么（依据 MAA 源码精读与 MaaFramework 协议），再标注哪些是引擎白拿的、哪些是我方纪律。

**阶段 0 · 取帧**
控制器截一帧，本轮全链路共用。现役 Win32 控制器的帧池截图与旧项目已验证的后台画面流同源（走系统合成层持续供帧，窗口被遮挡也能出帧）。**窗口锁定 1280×720**（列入启动检查项），此后全链路单尺度、统一坐标系，旧项目"十五档缩放循环"整体废除。

**阶段 1 · 公共打断链**
体力不足弹窗、公告、异常提示这类"随时会弹出来"的画面，每轮先于主链识别，命中即处理并跳回主流程。实现手段以跳回锚点模式为准（迁移设计 3.4 已验证的写法）；若所用协议版本含打断字段则直接选用。

**阶段 2 · 候选链判定**
按管线声明顺序逐个识别，命中即短路，后面的候选不看。命中位置记忆（上次命中区域局部复找）引擎内建。成本纪律：模板匹配毫秒级、文字识别百毫秒级——慢识别永远排在候选链靠后、且永远限定小区域。

**阶段 3 · 命中后的固定序列**
次数上限检查（超限则动作根本不执行、转出口链）→ 计数 → 前置等待（支持"等画面静止"）→ 执行动作 → 状态时间戳 → 按需回退他节点计数 → 后置等待 → 跳回 / 子流程。全部为引擎内建语义，我方只填数据。

**阶段 4 · 兜底迁移**
成功 → 下一步候选；次数用尽 → 出口链；绝对时限（默认 20 秒，可按节点放宽适配伊瑟的长加载画面）→ 失败链。任务失败自动存原始截图与标注图（引擎内建，默认开启）。

**贯穿不变量**
1. 动作之后帧作废，下一轮重新取帧（引擎行为）——旧项目所有"检测到再验一次""连续两轮才认账"补丁失去存在必要；
2. 同轮所有判定基于同一帧，优先级天然确定；
3. 每轮产生结构化回调（节点名 / 识别细节 / 耗时）——这是前端日志与问题定位的唯一来源，"找不到就刷屏"的文本噪音不复存在；
4. 失败现场按任务落盘，天然形成识别样本库。

**与"理想识别流程"专题讨论的对账**：九条采纳中七条由引擎内建直接承接（绝对时限＝timeout 字段；指纹跳轮的效果由节流＋等画面静止组合达成；打断清单＝公共打断链；位置记忆、单尺度、统一重试兜底、结构化事件、失败落盘均为内建），自建仅两条：拟人化点击（封装进自定义动作，后期可选）、720p 锁定（一条启动检查）。

## 四、硬性规范（防屎山红线）

1. **单一事实来源**：interface.json 任务清单是唯一入口登记处，GUI 与 CLI 都由它生成；禁止再手写任何任务入口包装（旧项目 25 个手写入口是反例）。
2. **节奏与阈值只进数据**：等待、阈值、识别区域、重试参数一律写在管线节点里，禁止散布在代码中（旧项目 0.7~0.88 内联阈值是反例）。
3. **等待原语唯一**：等画面 = 节点等待参数 + 绝对时限 + 失败链；禁止新增"睡眠后查一次"式轮询，存量只删不增。
4. **逃生舱唯一**：复杂逻辑只允许走自定义识别 / 自定义动作；禁止在编排层写流程分支。
5. **双轨期退役规则**：一个功能在新引擎验收通过后，旧实现**同一次提交内删除**；旧 core/ 只许变小不许变大。
6. **模板规范**：模板图命名与管线节点名严格镜像；统一 720p 裁剪；公共模板进 common/，禁止跨分类复制。
7. **观测强制**：每个任务必须产生结构化回调并具备失败存图；接不上事件的迁移不算完成。
8. **输入通道唯一**：全部经控制器下发，禁止散装调用系统输入接口。

## 六、模拟器模块（封存待接入）

**现状**：EtheriaMaa 仓库保持 P0 完成态——引擎绑定、资源加载、模板 / 文字识别 / 滑动链路、自定义扩展探针均验证通过，测试全绿。

**暂停原因**：伊瑟最新版本目前没有任何主流模拟器可运行。该阻塞取决于模拟器厂商，非我方可解；在此之前，模拟器侧任何开发都无法对真实最新版本验证，做了等于白做。

**封存期纪律（三条）**
1. ADB 相关代码原样保留，不删、不改、不继续开发；不参与 PC 主线的构建与发布。
2. PC 主线**禁止为模拟器预埋任何分支或判断**——两端解耦靠"同一套管线资源 + 控制器声明切换"，不靠代码互相渗透。
3. P1~P3 的一切产出天然控制器无关（这本来就是架构），封存不产生任何未来返工。

**重启条件（可观测、可判断）**：任一主流模拟器（MuMu 12 优先）能稳定运行伊瑟最新版本且无反模拟器拦截。

**重启清单（届时照做，预计 2~3 天恢复到可验证状态）**
1. 安装该模拟器，设 1280×720，开启 ADB；
2. 接口声明中切回 / 增加 Adb 控制器；
3. 已迁移完成的功能对真机回归，两端 UI 差异处补多模板兜底；
4. 恢复《MaaFramework迁移架构设计》中 ADB 相关验证项与原排期。

**接入后的形态**：同一套任务清单，用户在启动时选择连接方式（PC 窗口 / 模拟器），其余零差异。

## 七、总体审阅自查

**旧计划条目 → 新落点映射**（确保讨论过的不丢失）：

| 旧路线条目 | 新落点 |
|---|---|
| 识别层收敛（统一识别器 / 模板缓存 / 单尺度 / 等待原语唯一化） | 引擎内建 + 第四章规范 2/3/6 |
| Tasker 单线程 + 回调调度 | 官方绑定编排层（P1） |
| 自研管线执行器六件套 | 管线数据（引擎内建语义，P1~P2） |
| 通用导航器 | 公共导航节点 + 失败链（P1 起随功能沉淀） |
| 容错：重试表达等待 + 协作停止 | 引擎绝对时限 / 失败链内建 |
| 可观测：结构化回调 + 失败存帧 | 引擎内建；样本回流在 P4 |
| 注册表驱动 GUI / CLI | interface.json（P1 起即生效） |
| 断点续跑 / 进度持久化 | 编排层（P3） |
| 打法文件 / 掉落统计 / 资源热更新 | P4 |
| 工程止血 | P0A 门禁后方可标记完成 |

**讨论结论覆盖核对**：MAA 每轮判定顺序的六大精华（单帧复用、按序短路、位置记忆、次数状态机、统一重试兜底、失败落盘）→ 第三章逐条标注；"理想识别流程"九条采纳 → 第三章末尾对账；模拟器剥离与无缝接入 → 第一、六章。

**架构自查**：分层单向依赖 ✓；逃生舱唯一 ✓；双轨期有强制退役机制 ✓；封存模块与主线零耦合 ✓；单一事实来源唯一 ✓。

**遗留风险与对策**：
1. Unreal 窗口截图兼容性 → 兜底预案：现有常驻画面流封装为自定义控制器；
2. 模板放大 4/3 的识别精度 → P1 起对高频模板重裁；
3. 前端改造量 → P3 一次性完成，期间旧前端照常可用；
4. 检测风险 → 模拟点击性质不变；模拟器接入时需重新评估其检测面。
